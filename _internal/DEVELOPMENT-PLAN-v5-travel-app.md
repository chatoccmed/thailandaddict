## D. Verification Engine — แม่นโดยไม่ต้องไปเอง (owner ข้อ 1)

### D.1 หลักการ
ทุกข้อเท็จจริง (เปิด/ปิด, เวลา, ราคา, พิกัด, halal, ทางลาด, ตารางเรือ ฯลฯ) เก็บเป็นเรคคอร์ดแยก:
```
fact { placeId, field, value, sources[{type, url, seenAt, quote}], verifiedAt, method, confidence: high|medium|low|unknown }
```
- **high** = ≥2 แหล่ง **อิสระต่อกัน** ตรงกัน และ ≥1 แหล่งเป็น "ต้นทาง" (เจ้าของสถานที่/หน่วยงานรัฐ/ผู้ให้บริการจริง) ภายในรอบอายุของข้อมูลนั้น
- **medium** = 1 แหล่งต้นทาง หรือ 2 แหล่งรองที่ตรงกัน · **low** = แหล่งเดียวที่เป็นรอง · **unknown** = ไม่มี → แสดงว่า "ไม่ทราบ" ห้ามเดา
- แหล่งขัดกัน → เข้า **คิวตรวจโดยคน** ก่อนเผยแพร่ ไม่เลือกค่าเอง
- หน้าเว็บ/แอปแสดง badge: "✔ ยืนยันจาก 3 แหล่ง · 12 ต.ค. 2026" และ schema ใส่ `dateModified`
- รอบตรวจซ้ำตามความผันผวน: กฎเข้าประเทศ ≤120 วัน (มี gate แล้ว) · ตารางเรือ/ฤดู 30 วัน หรือก่อนเปลี่ยนฤดู · เวลาเปิดร้าน 90 วัน · สถานะโรงแรม/สถานที่ 180 วัน · พิกัด เมื่อมีแหล่งใหม่ขัด

### D.3 ทำงานอย่างไร
1. **Agent ตรวจ (Claude ผ่าน Batch API ลด 50%)** อ่านแหล่งตามตาราง → สกัดค่าพร้อมคำพูดอ้างอิง (quote) และ URL → เขียน fact record
2. **ตัวตรวจแบบ deterministic** (โค้ด ไม่ใช่ AI): แหล่งอิสระจริงไหม, วันที่อยู่ในรอบไหม, ค่าขัดกันไหม → ให้ confidence
3. **คิวตรวจโดยคน** สำหรับขัดกัน/ความเสี่ยงสูง (วีซ่า, สุขภาพ, ความปลอดภัย, ปิดถาวร)
4. **Gate ใน build** แบบเดียวกับ `check-entry-rules.mjs`: ข้อมูลหมดอายุ = build แดง
5. **Live check** หลัง deploy ทุกครั้ง (วิธีเดิมที่พิสูจน์แล้ว: เขียนก่อน deploy และพิสูจน์ว่าล้มก่อน)

## E. แพลตฟอร์ม: เว็บ + iOS + Android บนข้อมูลชุดเดียว (owner ข้อ 2)

```
                ┌──────────── Data Platform (Cloudflare) ────────────┐
 Verification → │ D1 (places, facts, sources, legs, constraints,      │ → Website (Astro: SEO/AI citation)
 Engine         │     trips, users) · R2 (รูป, offline packs)         │ → iOS app  ┐ React Native + Expo
                │ Worker API v1 (REST) + MCP server (สำหรับ AI agent) │ → Android  ┘ (โค้ดชุดเดียว)
                └─────────────────────────────────────────────────────┘ → ChatGPT/Gemini/agent อื่น (MCP)
```

**เว็บไซต์ (ยังสำคัญ — คนอ่าน/วางแผน + Google/AI อ้างอิง)**
- Astro สำหรับหน้าหลัก/hub/คู่มือ · หน้า long-tail (รีวิว, คำแปล, roundup) render จาก D1 ผ่าน Worker + cache ที่ edge → **ไม่มีเพดานไฟล์อีก**, build เฉพาะที่เปลี่ยน
- ระยะสั้น: Workers Paid ($5/เดือน → 100k ไฟล์) แล้วเอาคำแปล 2,384 ไฟล์ที่พักไว้กลับขึ้น
- PWA เป็นสะพานระหว่างรอแอป (offline ทริปที่บันทึก)

## H. Travel Planner เฉพาะทางไทย — สเปก (owner ข้อ 5)

**อินพุต:** วันที่ (หรือเดือน) · สนามบินเข้า-ออก · กลุ่ม (อายุเด็ก, ผู้สูงอายุ, การเคลื่อนไหว) · งบ · ความสนใจ · อาหาร (halal/มังสวิรัติ/แพ้) · จังหวะ · ภาษา · ที่อยากไปแน่ ๆ · ที่บันทึกไว้/วิดีโอที่วางลิงก์

**ข้อมูลที่ planner ใช้ (ต้องสร้าง):**
1. `constraints` — อุทยานปิด (สิมิลัน 16 พ.ค.–15 ต.ค., มาหยา 1 ส.ค.–30 ก.ย. ฯลฯ), ฤดูมรสุมแต่ละฝั่ง, เรือเสี่ยงยกเลิก, ร้อนจัด, หมอกควันเหนือ, เทศกาล, วันหยุดราชการ
2. `legs` — ตารางเดินทาง ~300+ ขา (โหมด, ชั่วโมงประตูถึงประตู, เที่ยวแรก/สุดท้าย, ราคาช่วง, เสี่ยงอากาศ) — ขา >4 ชม. = วันเดินทาง
3. `hours` — เวลาเปิด-ปิด/วันปิด ของสถานที่ (เริ่ม 500 จุดยอดนิยม)
4. `places` + `facts` + confidence (ส่วน D)

**ผลลัพธ์:** แผนรายวันพร้อมเวลา · ขาเดินทาง + ลิงก์จอง · ย่านที่ควรพักแต่ละคืน (ลดการย้าย) · งบประมาณ · ไทม์ไลน์ "ต้องจองอะไรเมื่อไร" (.ics: TDAC 3 วันก่อน, รถไฟ 90 วัน, ยี่เป็ง, Michelin) · checklist สุขภาพ/ของที่ต้องพก · offline pack · แผนสำรองวันฝน · แชร์/แก้ร่วมกันกับเพื่อน (โหวตกิจกรรม) · ส่งออก PDF/ปฏิทิน/Wallet

**การทำงาน:** แผนสำเร็จรูป (258 itinerary ที่คนตรวจแล้ว) ขึ้นทันที → AI ปรับตามอินพุตด้วย tool use (`search_places`, `get_facts`, `get_legs`, `check_constraints`, `get_hours`, `estimate_budget`, `booking_options`) → validator ตรวจ → อธิบาย "ทำไมจัดแบบนี้" + ทางเลือก

**จุดรายได้ในแผน:** ทุกคืนมีปุ่มจองที่พัก (เทียบ Agoda/Booking/Trip) · ทุกขาเดินทางมี 12Go/เที่ยวบิน · ทุกกิจกรรมมี Klook · ก่อนเดินทางเสนอ eSIM + ประกัน (เป็นรายการใน checklist ไม่ใช่ป๊อปอัป) · แจ้งราคาลดจริงเมื่อผู้ใช้เปิด

**เรียนรู้:** ผู้ใช้แก้แผนตรงไหน → ปรับ template/constraints (ไม่เก็บข้อมูลส่วนตัวเกินที่ยินยอม)

**North star:** "ทริปที่ใช้จริงระหว่างเดินทาง" ต่อเดือน

## L. สิ่งที่จะไม่ทำ

- ไม่ scrape/เก็บข้อมูล Google Maps, Street View, TripAdvisor หรือ OTA นอกช่องทางที่อนุญาต · ไม่ใช้ข้อมูล Google ฝึก/ทดสอบ AI
- ไม่ใช้ AI แต่งสถานที่ รีวิว ธง halal ข้อมูล accessibility เวลาเปิด — ไม่รู้ = "ไม่ทราบ"
- ไม่อ้างว่า "ไปมาเอง" ถ้าไม่ได้ไป (ใช้ "ยืนยันจาก N แหล่ง" / "ยืนยันโดยสถานที่" / "ผู้ตรวจท้องถิ่นถ่ายเมื่อ…")
- ไม่มี dark pattern ทั้งในเว็บ แอป สมาชิก และ push
- ไม่ขายอันดับ · ไม่สร้างระบบจ่ายเงินเอง (ใช้ partner)
- ไม่ทำ Flutter/2 codebase native แยก

## M. ความเสี่ยง

1. **ข้อตกลงผู้ให้ข้อมูล** (Google, OTA, รีวิว) — ฝ่าฝืน = โดนตัด API/ฟ้อง → VERIFICATION-POLICY + review ก่อนเพิ่มแหล่งใหม่
2. **ข้อมูลผิดในแอปที่คนใช้หน้างาน** (วีซ่า สุขภาพ เรือ) — เจ็บกว่าเว็บ → confidence + gate + live check + คิวคน
3. **Apple/Google ปฏิเสธแอป** — ต้องมีฟีเจอร์ native จริง, ลบบัญชีในแอป, privacy label ครบ
4. **ต้นทุน AI บานปลาย** — quota, cache, แผนสำเร็จรูป, Batch API, วัดต้นทุนต่อทริปที่ใช้จริง
5. **PDPA/GDPR** — ทริปและตำแหน่งเป็นข้อมูลส่วนบุคคล → ยินยอมชัด, เก็บน้อยที่สุด, ลบได้
6. **Google AI Mode / OTA ทำ planner เอง** — ชนะด้วยความลึกเรื่องไทย + ข้อมูลตรวจแล้ว + ออฟไลน์ + 9 ภาษา + หมอ
7. **ภาระ owner คนเดียว** — AI เขียนโค้ดส่วนใหญ่ได้ แต่บัญชี store, สัญญา, ผู้ตรวจท้องถิ่น, วิดีโอ ต้องใช้คน → อาจต้องจ้าง mobile QA/ผู้ประสานงานพาร์ทไทม์
8. **เครื่อง build** — repo บน USB HDD, C: เหลือ 6 GB → ย้าย build ไป CI (GitHub Actions/EAS) ใน Phase 1
