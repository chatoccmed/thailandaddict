## North-star (ปรับ)
Thailandaddict's Trip Planner should be the most TRUSTED Thailand itinerary tool — not the flashiest. It turns the site's real, honesty-locked content graph (1,939 reviews + 215 roundups + 3,347 articles across 77 provinces) into a believable day-by-day "trip briefing" that every traveler can verify, carry offline, and book through TA's affiliate partners. Thailand-first and Thailand-branded: this is the wedge that compounds SEO + bookings, NOT a global planner. The global play is a SEPARATE product on a SEPARATE domain that reuses this UX shell with a pluggable content provider — sketched in the architecture now, built later. v1 ships as a trusted, measured, mobile-first, server-saved briefing; the "app" path is unlocked cheaply by saving trips as server objects (KV) from day one so there is no rewrite to PWA/Capacitor later.

## Headline reframe
The single most important reframe: ship v1 as a "trusted trip BRIEFING," not a precise play-by-play SCHEDULE — because the data to back exact times does not exist yet, and a wrong "20 min" destroys the trust that drives every booking. I verified the feeds (`gen-feeds.mjs`): hotels/restaurants/attractions have NO coordinates, NO affiliate deep-links, and NO phone/hours — restaurants do NOT have coords (a common assumption in the critique is wrong). So three of the loudest recs need adjusting: don't promise exact travel times, don't validate "affiliate links per item" (the feed only carries TA page URLs — affiliate links live on those pages), and don't claim lat/lng is a quick add. The two true must-dos that gate everything: (1) install GA4 + UTM before launch so you can measure, and (2) save trips as server objects in Workers KV so the app/share/global paths are cheap later.

## 📱 APP PATH
- Save trips as server objects in Workers KV from v1 (tripId is the permission model; link = access). This is THE decision that prevents a rewrite — the entire app/PWA/Capacitor path needs server-saved trips + sync, and retrofitting accounts onto localStorage-only is weeks of work.
- Store only tripId in localStorage, never the full itinerary — so a future account simply claims tripIds by email; no data migration of large blobs.
- Publish a versioned, API-first ITINERARY_SCHEMA (version field + Worker-side validation) so swapping AI providers or building a native client never breaks the data contract.
- Wrap localStorage (ta_wishlist) in a versioned accessor with a migration function now — adding fields later (type/city/province already planned) won't corrupt returning users' saved items, which matters doubly on app updates.
- Anonymous trips with 30-day KV TTL in v1; v2 adds optional email to 'claim + make permanent' — designed so guest→account conversion has zero upfront friction.
- Keep all interactive logic in the Worker/API layer (not baked into Astro pages) so a PWA shell or Capacitor wrapper can call the same /api/trips endpoints unchanged.

## 🌏 GLOBAL PATH
- Global is a SEPARATE product on a SEPARATE domain — 'Thailandaddict' is geographically locked in brand, domain, SEO, and tagline ('ชีวิตติดเที่ยว ทั่วไทย'). A 'Thailandaddict Japan' destroys trust and dilutes the Thailand SEO moat. Thailand is the flagship; let it compound.
- The candidate-pool model does NOT extend globally — TA's homegrown feeds cannot out-review Wanderlog/Google/Booking for 50 countries. The global product must use a pluggable content provider (Booking/Google Places/Tripadvisor APIs), not homegrown JSON.
- Sketch the abstraction NOW without building it: have /api/trips take a contentProvider param (v1 = 'local' reading /feeds; global v2 swaps to 'api') so the AI orchestration and UX shell are reused, not rewritten.
- Global travel times REQUIRE a real directions API (Google/OpenRouteService) — AI geo-estimates work passably for Thailand only because the model knows Thai roads; they're 30-50% wrong elsewhere. The estimateTravelTime() function should be a swappable module from day one.
- What's genuinely reusable globally: the UX funnel (save→plan→share), the honesty-lock principle, the JSON schema, the booking-summary pattern, the infographic. The brand, content, and geo-knowledge are not.
- Honest take: prove the FORMAT in Thailand first (does anyone finish the form? do plans convert?). Only spin the global product once Thailand shows the funnel works — otherwise you build a global content-sourcing problem on top of an unproven format.

## 🙂 EASE WINS

- Progressive disclosure of the form: days → provinces → travel-style cards (pace+interests combined into Chill/Balanced/Packed) → transport → optional 'who's traveling'. Cuts perceived load from 8 fields to ~4 visible at a time on mobile.
- Pre-fill provinces and must-include toggles from saved items — respects the user's saves and removes a re-entry step.
